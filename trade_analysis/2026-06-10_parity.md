# Backtest ↔ Live Parity Check — 2026-06-10

**Question:** does the backtest system reproduce today's live trades given the same
config (`bot_config.json`, faithful `strategy_params` path) and the same 1min bars?

**Setup:** fetched 2,760 1min bars per instrument (06-08 20:48Z → 06-10 20:47Z,
TopstepX API) into `bars/bars_{MGC,MNQ,MES}_1min_20260610.csv`. Ran
`python -m app.backtest` per instrument with `--no-risk-limits` (live hit no
lockouts today; the backtest's hardcoded 50k-combine limits would inject
artifacts at a 153k balance). Results in `backtests/parity_{INST}_0610.json`.
Backtest code includes the fib fix (07d4410); live ran the broken fib until the
20:47Z restart — grade differences on matched trades are expected.

**But the backtest is NOT trustworthy end-to-end yet**, for two reasons:

### 1. Confirmed fill/entry-price bug (inflates backtest P&L)

Several backtest entries record prices far outside the bar range at fill time:

| inst | time | recorded entry | actual bar range |
|---|---|---|---|
| MGC | 02:33 | 4361.20 | 4197.8–4202.6 (**~160 pts off**) |
| MNQ | 14:29 | 29228.50 | 29136–29181 |
| MES | 18:00 | 7398.25 | 7327–7333.5 |

4361 is an 06-08 price level — these look like armed zones created on stale prices
"filling" long after they should have been invalidated, and/or `entry_price`
recorded from the signal rather than the simulated fill. Repeated identical entry
prices on consecutive trades (e.g. MNQ 28782.50 at both 18:18 and 18:32) point the
same way. This poisons the backtest stats (+$21k combined, ~60% WR vs live −$488,
22% WR). **Do not trust backtest P&L until this is fixed.**

### 2. Trade-count divergence

- **31 backtest-only entries**, heavily clustered 02:00–05:00 (London) — live took
  zero trades 01:32→07:14. Either the live feed/process had a quiet gap, or live
  armed-zone/grader state (e.g. HTF-dependent premature-liquidity cancels, which
  the backtest never feeds) suppressed them.
- **9 live-only entries** (MES 01:21, MNQ 01:22, MGC 08:37 + 09:19, MNQ 10:09,
  MNQ/MES 13:36-37, MNQ 16:26, MNQ 17:07) — backtest state diverged after extra
  trades occupied the one-zone-per-instrument slot, plus intrabar fill differences.

## RESOLVED 2026-06-11 — root cause was stale-FVG inversion, not armed zones

These configs ran `ifvg_entry_mode: "close"`, which bypasses ArmedZoneTracker
entirely. The real mechanism: `DisplacementDetector._find_inverted_fvg` matched
any active FVG whose far edge lay beyond the displacement bar's close — no
requirement that THIS bar did the closing-through, and no removal after a match.
Hours-old FVGs far from price "inverted" repeatedly, and `_build_signal` sets
entry = FVG edge, so entries landed up to 70 pts outside the signal bar
(replayed and confirmed via `scripts/diag_stale_fvg.py`).

Fix: inversion now requires the previous bar's close on the near side of the
far edge (`displacement.py`), plus armed-zone expiry (`ifvg_zone_max_age_bars`,
default 120) and a PaperBroker stale-entry guard (`max_entry_slippage_frac`).

Re-run on the same bars/configs (`backtests/parity_*_0611_postfix.json`):

| inst | trades | net P&L | win rate |
|---|---|---|---|
| MGC | 54 → 37 | +$6,822 → +$682 | 63% → 40.5% |
| MNQ | 82 → 47 | +$9,979 → −$1,176 | 62% → 36.2% |
| MES | 61 → 45 | +$4,559 → −$376 | 59% → 46.7% |

Combined +$21,360 → −$870 vs live −$488 — the fantasy P&L is gone. The
repeated-identical-entry symptom is gone (one benign opposite-side repeat).
**Every backtest result produced before this fix — including the MNQ 5min
walk-forward — was generated with the buggy signal path and needs re-running.**
Trade-count divergence vs live (HTF feed gap, London cluster) remains open.
